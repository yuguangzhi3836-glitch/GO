# GO 开发与香港运营职责决定

记录日期：2026-09-09  
权威来源：用户在当前 GO 指挥中心对话中的明确决定。该决定适用于全系统，包含支付、业务规则、前后端、接口适配、数据库迁移及部署工具代码。

> 我们的支付系统是不是己经做好了只等接口连接了？香港也在另做一个支付系统，所有的系统开发要以指挥中心的为准，香港的只负责运营，不能改开发！

## 职责

| 工作 | 指挥中心 | 香港运营 |
|---|---|---|
| 架构、业务规则、代码开发及缺陷修复 | 统一负责并形成可审核变更 | 收集需求、故障和原始证据；不得自行改代码 |
| 支付渠道适配与执行器 | 在统一源码中开发、隔离测试、封包 | 按批准方案完成运行配置；不得另建支付系统或现场补写适配器 |
| 版本与交付 | 绑定源码、依赖、包 SHA256 与验收范围，产出封存候选 | 仅按明确批准的版本和任务执行运营操作 |
| 发布与回滚 | 提供经审核的方案和证据，遵循用户授权与顺序门禁 | 仅在具体授权范围内执行；不自行决定升级、回滚或重新部署 |
| 香港侧既有开发成果 | 接收原始代码与差异说明，决定是否纳入统一候选 | 保留原始成果和运行状态，提交审阅；停止新增开发，不自行覆盖线上系统 |
| 运行反馈 | 判断修复与验收方案 | 日常监控、运营处理、问题复现及回传证据，均受现有授权范围约束 |

指挥中心统一开发不等于自动获得合并、部署或生产变更授权。香港“只负责运营”也不构成扩大运营权限；现有冻结、只读、备份及单次任务要求继续适用。

## 支付代码边界

DEPTH29 目前将 PSP sandbox delegate 留作外部注入。这个扩展机制不授予香港开发权限。所需渠道执行器也必须由指挥中心完成开发、测试和版本封存；香港只运行经批准的成品与配置。

用户表示香港在另做支付系统。本次没有取得该系统源码或执行记录，记录为用户提供的情况，不推断其已部署或已触发真实支付。既有成果先保留并归并审阅，不清除、不覆盖，不平行发布。

本次只增加治理文档和支付审阅结论，不改变封存候选、权限设置、香港运行环境或资金状态。任何后续工程实现仍须保留原成果，使用独立候选并完整记录谱系。
