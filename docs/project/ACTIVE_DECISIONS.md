# GO ACTIVE DECISIONS

> Purpose: record currently effective human/project decisions without requiring a new session to replay historical chats or PRs.
>
> This is an append-preserving decision register. Do not silently rewrite history when a decision changes.

## Decision lifecycle

Each decision uses one of these states:

- `ACTIVE` — currently effective.
- `PARTIALLY_SUPERSEDED` — some scope was replaced; the surviving scope remains effective.
- `SUPERSEDED` — no longer effective; replacement must be named.
- `HOLD` — considered but not currently effective.
- `UNKNOWN` — evidence is insufficient; AI must not fill the gap.

When a decision changes:

1. keep the old entry;
2. mark its new status;
3. add a new decision with a new ID;
4. link `supersedes` / `superseded_by`;
5. state whether the change affects only future work/orders or existing state as well;
6. perform impact review before code/runtime mutation.

## Human-readable decision rule

Business owners should normally be asked to decide outcomes in plain language, not implementation terms.

Example:

- Business decision: "If the hotel cannot confirm the room, the guest must not be left with a final successful room charge."
- Technical implementation: authorization/capture/void/refund/state machine details are derived and reviewed separately.

Changing technical implementation does not automatically mean the underlying business decision changed.

## AI conflict rule

Before implementing a new business decision, AI must check whether it conflicts with an existing `ACTIVE` decision.

If a conflict is found, output:

1. new proposed decision;
2. conflicting active decision IDs;
3. affected modules/flows;
4. effect on existing orders/state versus future orders/state;
5. required human decision;
6. required tests/migration/runtime review.

Do not silently overwrite the older rule.
