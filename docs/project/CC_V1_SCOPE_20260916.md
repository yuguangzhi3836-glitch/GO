# Command Center V1 范围重置（权威）· 2026-09-16

> 本文件是 GO Command Center V1 的**范围契约**。当它与任何更早的安全设计、Issue 正文、
> 组件 README 或 PR 描述冲突时，**以本文件为准**。它由 Eason 于 2026-09-16 01:02 正式下达。
>
> 一句话：**V1 的目标是让老板只通过 ChatGPT 就能安全、快速地把 GitHub 新版本部署到 HK-STAGING。**

---

## 一、产品目标（V1 的唯一成功标准）

```text
Boss → ChatGPT → “部署这个版本到香港测试环境”
     → GitHub bounded Request → Command Center → HK Agent → 受控 Executor
     → 部署 → Evidence → 自动 VERIFY → ChatGPT 返回结果
```

老板**不得**需要：SSH、WorkBuddy、Codex、Eason 中转、手工执行服务器命令、
手工生成或操作密码学密钥、手工签 JSON、手工维护 deployment plan。

以上任何一项，只要成为完成部署的必要步骤，**就是 V1 未达标**，而不是「操作规范」。

```text
做到上述流程  ⇒  COMMAND_CENTER_V1=DELIVERED
而不是等所有理论安全问题都解决才算完成。
```

## 二、V1 威胁模型（已收缩）

合法操作者 = 项目当前授权的**两个 GitHub 用户**。

Human Approval 的 V1 权威 = 以下四者之合：

```text
authenticated GitHub identity      （GitHub 自己保证的作者身份）
+ explicit approval intent         （明确的审批意图，而非仅"创建了 PR"这类隐含信号）
+ candidate binding                （绑定到确切候选提交）
+ environment binding              （绑定到 HK-STAGING-01）
```

### 立即取消的 V1 blocker（不再是 blocker，不再要求，不再检查）

```text
DEDICATED_HUMAN_APPROVAL_PRIVATE_KEY
APPROVAL_SIGNER_ROTATION
APPROVAL_SIGNER_FINGERPRINT_LIFECYCLE
HUMAN_APPROVAL_SIGNER != TASK_SIGNER
HUMAN_MANUAL_CRYPTOGRAPHIC_SIGNATURE
```

```text
⛔ 不要创建新的 Human Approval private key。
⛔ 不要要求用户手工签任何 approval artifact。
⛔ 不要把上一轮为「独立审批签名者」做的实现当作资产保留 —— 它属于已取消的范围。
```

## 三、V1 保留的密码学身份（只有两个）

```text
Command Center Task Signer     → 证明 CC 发出了什么 Task
HK Agent Evidence Signer       → 证明 HK Agent 实际执行出了什么结果
```

两者**继续要求身份分离**（不同密钥）。除此之外不再要求任何签名身份。

## 四、V1 仍然强制的安全边界（一律**不得**降低）

```text
bounded action allowlist          fixed HK-STAGING environment
immutable GitHub source binding   candidate commit / PR binding
no arbitrary shell                no arbitrary argv
no arbitrary image from caller    no arbitrary path
no arbitrary service              no arbitrary environment
Task identity                     nonce / replay protection
duplicate execution protection    Signed Evidence
failed execution Evidence         rollback to known-good target
post-deploy VERIFY                fail closed on uncertainty
Production excluded
```

## 五、停止安全功能扩张（新规则的执行方式）

每发现一个问题，先问：

```text
QUESTION: Does this prevent the Boss from safely completing
          ChatGPT → GitHub → CC → HK Agent → Deploy/Rollback?
  YES → fix now
  NO  → 记为 TECHNICAL_DEBT / V2，不扩 V1
```

禁止因为「存在理论攻击路径」继续新增：signer、authority layer、gate、
approval subsystem、status state、schema、daemon、timer、workflow
—— 除非它**直接阻断** V1 核心 E2E。

## 六、#103 的收口目标（不再追求企业级 deployment control plane）

只需证明该链路成立，并满足：

```text
TEST_PR=PASS      VERIFY=PASS
CANARY=PASS       （在现存 live executor 要求它时）
RELEASE_GATES=PASS（在现存 live executor 要求它时）
DEPLOY_READY=YES
```

**不要新增新的 gate。**

## 七、剩余队列（最短路线）

```text
1  liveness continuity                    ✅ 已完成并登记 #98_LIVE_CONTINUITY=PROVEN
2  dedicated TEST_PR Builder V2           ✅ 已完成（首张成功 TEST_PR 39d11b5e102e）
3  GitHub authenticated approval 取代独立 Human Approval signer   ← 本轮
4  重跑 TEST_PR / VERIFY / 现存 live gates
5  DEPLOY_READY=YES
6  停止，请求人类确认真实 HK-STAGING DEPLOY
7  执行一次真实 DEPLOY
8  Evidence + VERIFY
9  关闭 #103
```

```text
#104 最小 Rollback Eligibility（current release / previous known-good /
     rollback target binding / ROLLBACK_READY；不做通用 release management）
#105 一次真实 ROLLBACK + 独立 VERIFY（另需独立 Human Approval 才可动真实 HK）
#106 只防 duplicate execution / nonce replay / blind retry /
     Evidence missing 导致重执行 / restart 导致重复 task
#107 冻结五种 intent：status / verify / test_pr / deploy / rollback，不再增加命令
#108 只做最终验收与文档收口，禁止新增功能
```

## 八、时间 / 成本原则

```text
DELIVERY > THEORETICAL PERFECTION
SIMPLICITY > EXTRA SECURITY LAYERS
PROVEN E2E > MORE ARCHITECTURE
```

任何新设计若明显增加 API token cost / implementation time / CI surface /
operational complexity，但不直接提高「两人团队对 HK-STAGING 的自动部署成功率」，
则推迟到 **V2**。

## 九、TECHNICAL_DEBT / V2 登记（本节由后续发现追加，**不在 V1 修复**）

| 编号 | 内容 | 为何不阻断 V1 |
|---|---|---|
| TD-01 | 独立 Human Approval 密码学签名者、其轮换与指纹生命周期 | 职责已由 authenticated GitHub identity 承担（范围重置） |
| TD-02 | `task_not_claimed` 把认领前的全部拒绝理由压成一个标签（SCHEMA/ENV/AUTHORITY/SIGNATURE/EXPIRY/REPLAY/ATTEMPT/ALLOWLIST/PARAMETERS 都读不到真因） | 只影响排障效率，不影响部署成功率 |

| TD-05 | `LIVE_SWITCH_PROVENANCE` 的历史 enable 来源未追认 | 当前开关为 false，且 V1 不要求追认历史 |
| TD-06 | state publication `runs/` 的 retention 策略 | 与部署成功率无关；最迟 #108 前成形 |

## 十、本重置明确**不**改变的东西

```text
Production 仍然排除在外
`deployment_requests_enabled` 仍为 false（真实 DEPLOY 需人类明确批准后才开）
真实 HK-STAGING DEPLOY 与 ROLLBACK 仍需当次人类批准
PR #109 的合并仍需人类最终 Review
```

范围收缩**只**取消「以密码学方式证明审批者与 Task 签名者不同」这一项要求，
不取消任何执行边界、不取消 fail-closed、不取消 Production 隔离。

> **2026-09-17 更正（只增不改，原文保留）**：上面 `deployment_requests_enabled` 那一行属于
> **2026-09-16 当时状态**。该开关此后**已退役**——部署不再由开关控制，而是由「一次经 GitHub 身份
> 认证的 DEPLOY Request」**本身**授权（现场通道 `deployment_authorization: "request"`，六项 action
> 全开）。因此本节「不改变的东西」第 2 项按新口径读作：**没有常备授权，每份 DEPLOY Request 自己
> 就是当次授权**；其余三项不变。判据以现场通道配置为准，不以任何派生文档为准。
