## 2. 容量口径与计算

在线用户：在规定会话活跃窗口内仍在使用平台的独立用户；正式观测窗口拟为 5 分钟，并同时统计瞬时活动请求。不能用累计注册数、空闲 TCP 数或健康检查请求替代。

初版压力包络是设计假设，不是业务预测或采购清单：

| 参数 | 初版假设 |
| --- | --- |
| 在线用户 | 1,000,000 |
| 每用户平均动态请求间隔 | 10 秒 |
| 持续动态请求 | 100,000 RPS |
| 峰值倍率 | 3 倍，即 300,000 RPS |
| 额外保留容量 | 30%，对应约 428,572 RPS 总处理能力目标 |
| 查询分布 | 浏览 60%、搜索 25%、Trips/状态 10%、交易命令 5% |

交易命令包含报价确认、下单、支付发起、取消、退款和状态操作，不等于每秒实际成交订单数。所有响应的缓存命中/未命中、后端扇出及重试单独计数。供应商请求量按搜索缓存未命中 × 扇出 × 重试放大计算，再按供应商合同限额约束，不能把平台 RPS 全数转发给供应商。

图片、静态资源 CDN 字节带宽独立测算；AI 会话流式连接、推送连接、邮件和后台任务均有独立容量模型，不默认百万用户同时调用模型。AI 超时或限额时，普通浏览和既有交易流程必须仍可工作；自动执行不得绕过原有交易授权。

`ci/capacity/model.py` 仅做离线算术与预算拒绝，不发请求。`planning-example.json` 中数据库示例是小型隔离环境预算，绝不代表百万人所需数据库配置。

## 3. 架构决策

1. 保留 Python 业务实现，按测量选择局部 Go/Java 等服务；不在无证据时整体重写。阶段一维持现有业务服务角色。
2. 查询侧与交易侧逐步隔离资源：CDN/缓存/搜索读模型承接查询；库存/订单/资金保持明确权威。缓存里的房量和价格不能成为最终下单事实。
3. API 可横向扩容的前提是会话、幂等、限流、租约和任务状态不依赖单进程内存。逐项审计后才启用多实例；本批没有声称完成这一审计。
4. 区域单元独立限流、队列和数据库预算；订单/库存/账本有稳定归属。跨区域操作路由至归属区域，以可追溯补偿处理失败，不允许分区时两边同时扣减同一库存或资金。
5. 按业务域和数据归属规划分区，不先把所有模块拆成微服务。跨区个人信息、存储和支付安排另行核实；未来大陆部署不能依赖未经验证的跨境控制面可用性。
6. 供应商隔离超时/熔断/配额和有限重试；退款、支付未知状态采用持久化恢复，不能盲目重发。每个队列有积压年龄、重试上限、死信及人工处理出口。
7. 热点库存使用原子条件更新/短事务/幂等并通过同一房型日期、同一航班竞争测试；不能仅测试均匀分散对象。
8. 区域切换先验证资金与库存写入权的隔离、复制延迟和恢复流程，再改变流量路由。30% 容量余量不自动等于可以失去任意一个区域。

## 4. 本批实际代码

数据库配置增加 `DATABASE_POOL_SIZE`、`DATABASE_MAX_OVERFLOW`、`DATABASE_POOL_TIMEOUT_SECONDS`、`DATABASE_POOL_RECYCLE_SECONDS`。PostgreSQL 引擎使用这些参数；默认仍为 5、10、30 秒、-1，保留之前 SQLAlchemy 默认行为。拒绝零大小池、负溢出、无穷/NaN 等无界参数；SQLite 保持原来的方言池行为。池满时由现有调用栈接收超时，不添加自动事务重试。

集群连接预算为每个共享数据库上的 `Σ[(最大副本数 + 发布额外副本数) × 每副本进程数 × (pool_size + max_overflow)]`，再加其他连接、维护保留量。预算工具超过总额即失败。每个引擎都必须计入；此工具没有自动发现线上配置的能力。

池测试覆盖参数拒绝、环境变量生效、真实队列池耗尽/释放恢复、SQLite 内存兼容及隔离 PostgreSQL 实际连接竞争。它是正确性测试，不是高并发容量测试。多实例执行同一业务的竞争、HTTP 过载响应、供应商隔离以及真实吞吐仍待后续实现和验证。

继续检查首次启动发现身份初始化竞态：两个连接均查不到账号，再同时插入导致其中一个唯一约束异常。新增屏障同步的真实并发连接测试已在旧实现复现失败；修复为回滚后读取同名已提交账号，保留原密码/角色/租户；无同名账号的其他约束错误继续抛出。分别在 SQLite 和隔离 PostgreSQL 验证，不以进程内锁解决跨实例一致性。

参考：SQLAlchemy 官方连接池说明 https://docs.sqlalchemy.org/en/20/core/pooling.html 。连接池已有默认实现；本批解决显式配置和预算问题，并非声称之前没有连接池。

## 5. 阶段验收标准（设计目标）

既有隔离加压顺序保留：探针 → 20 → 100 → 250 → 500 诊断 → 1,000 → 2,500 → 5,000 → 7,500 → 10,000。随后设计 100,000、300,000、1,000,000 在线行为模型。每阶必须通过后再加压。此文不派发香港任务，也不授权对真实供应商或支付通道发压测流量。

- 持续负载 60 分钟、8 小时稳定性、2 倍阶段负载突发 5 分钟；有冷缓存、热点、长尾供应商及单实例故障场景。
- 初版平台目标：普通读取 p95≤500ms/p99≤1500ms；搜索 p95≤1500ms/p99≤3000ms；交易平台接收/处理响应 p95≤1000ms/p99≤2000ms。外部出票、支付和履约最终完成时间单列，不以快速返回“处理中”冒充履约成功。
- 目标负载内平台技术错误≤0.1%；429/503、超时、排队及被拒请求必须单独报告且计入未服务需求，不能筛除后宣称成功。
- 无超卖、重复资金副作用、跨租户访问或无法解释的账差；发生一项即本级失败。业务售罄与技术错误分列。
- 输出各业务 RPS、p50/p95/p99、数据库连接/锁等待/慢查询、CPU/内存、队列积压年龄、缓存命中、供应商扇出以及单位成功交易成本。
- 压测器验证自身未饱和，跨节点使用唯一账户/请求键；记录计划发送与实际发送、漏发、重试和完整延迟分布，防止系统变慢后压测器也少发请求而掩盖瓶颈。
- 固定 SHA、镜像、迁移、测试数据规模、硬件及资源限制；所有结果说明模拟边界。小样本不能线性外推百万在线达标。
