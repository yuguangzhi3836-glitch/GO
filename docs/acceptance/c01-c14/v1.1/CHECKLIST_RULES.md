# C13 完成验收清单审查规则 v1

本规则用于固定C01–C14内部工程完成义务，并审查后续候选。它是审核规则交付，不是业务实现或正式Runner实施，不变更PR247架构。前序ecab110746760ac46acec60f0c96545e02b90a66限定PASS保留为历史证据；未把该PASS分配给新清单或新版本。

## 1. 分母必须来自职责和需求

先冻结用户最新版职责、已有有效产品决定、各模块状态/接口/角色清单、跨模块合同及运营职责，再拆验收条目；不能从“已有测试/已实现代码”反推完整分母。未实现、待设计、依赖未交付、未知结果及真实用户页面缺失全部登记。所有已知未决需求进入需求登记，不能只写在报告备注而逃出分母。

每模块必须提交七类覆盖表：正常主链；错误/拒绝/超时/未知结果；角色权限与租户/对象归属；幂等/并发/中断/恢复；资金与跨域权威事实；用户/供应商/管理员及适用移动端真实交互；持续运营的内部可操作闭环。每类列出具体条目ID，禁止用一句“全覆盖”或单个万能测试替代。未知适用性记UNRESOLVED并阻止清单冻结；确实不适用必须给职责/合同依据，C13审查而非开发者自行排除。

每条是可证伪的一个业务/控制结果。需有触发、前提、输入角色、预期持久化状态、可观察结果和验证方式。重复同一义务的单测/API/browser/PG是证据层，不是四个完成分母。不同不变量（如拒绝越权、拒绝陈旧版本、并发仅一次）须独立条目。边界表/有限状态转换表可以一个条目引用完整case矩阵，但任一必需case未通过，该条目不能PASS。

跨模块边界各方列出自己的可观测责任，使用共享contract_id关联，不把同一项复制多次来抬高总数。C11拥有资金权威；各业务模块仍负责正确请求、授权边界和展示，不能把这些责任全部移出自己的清单。运营是C01–C14各自职责，不能统一推给C12或香港。

## 2. 冻结和变更

台账必须记录schema_version、checklist_version、scope_id、职责/决策来源、owner、每条稳定ID、冻结时间、清单内容hash和批准/审查记录。当前提案由root汇总并经C13完整性审查；不能用“清单已写好”冒充需求范围已经完整冻结。

新增/删减/拆合/不适用调整均产生新清单版本并附理由、旧新ID映射和分母变化；旧版本与历史统计保留。不得为到达100临时移除失败项、把未做项改成可选、降低UI为API、把PG改SQLite、缩小状态集合或拆出新范围而不披露。任务优先级可调整，已承诺范围不自动缩减。

外部真实供应商/PSP、物理真机、生产压力/SLA和正式Runner安装按用户既定范围独立列状态，不扣接入前内部分；但与其相关的内部权限、模拟合同、失败处理、配置校验、收据验证、可操作角色页面、报警/重试/人工接管能力仍在内部清单。不得以“外部未接”排除内部义务。

## 3. 建议条目字段

`id, cell, contract_id?, requirement_ref, category, actor, preconditions, trigger, expected_result, source_paths, verification_cases, evidence_requirements, dependencies, priority, applicability, implementation_state, evidence_state, review_status, evidence_refs, candidate_binding, reviewer, reviewed_at, stale_reason`。

- implementation_state：NOT_ASSESSED / NOT_STARTED / IN_PROGRESS / IMPLEMENTED；只表示开发状态。
- evidence_state：NONE / DESIGN_ONLY / DEVELOPER_ONLY / SUBMITTED / VERIFIED / STALE / INVALID；证据状态与实现状态分开。
- review_status：NOT_ASSESSED / BLOCKED / FAIL / PASS / NOT_APPLICABLE。不能把SUBMITTED、已派发、测试启动或开发自测当PASS。
- applicability：REQUIRED / PROPOSED_OUT_OF_SCOPE / APPROVED_OUT_OF_SCOPE / UNRESOLVED。审批人和依据必填；不适用项不能伪装为PASS。
- 优先级与阶段用于排序，不改变必需项是否计入完成分母。

## 4. PASS的证据约束

候选必须绑定完整commit、product commit（若门禁提交分离）、application tree、文件数/指纹、环境/数据库版本、规则与fixture版本、清单版本/hash、测试工具及运行ID。每条指向准确源码/测试case/原始结果；artifact SHA256、内部文件哈希及原始失败/跳过/取消状态可核。

涉及持久化和资金，不仅核返回码：核DB/账本、幂等键、owner/tenant、状态version、引用关联及重复请求副作用。涉及用户操作，必须用正常点击/输入走真实API且检查重载后的状态；禁止forceclick、直接写状态或绕过角色身份来冒充正常用户旅程。内部浏览器证据与物理真机分开。

涉及PG约束/锁/并发必须在隔离真实PG执行；SQLite不替代。跳过/未收集/取消/超时均非通过；可在同候选的适当环境补证，但原skip保留。测试套件数量与完整需求数量不是同一概念，重叠case不可累加作独立覆盖。

历史证据保持原source绑定。新候选默认NOT_ASSESSED/STALE；允许“逐项保留证据评估”，必须证明相关源码、依赖、规则、环境合同及测试义务未变，执行当前候选必要集成回归，由独立reviewer对新候选签发新的条目结论。引用旧PASS不等于新PASS；无法证明影响边界就重验。修复失败保留失败→修复→新固定候选的完整链。

## 5. 完成率算法与100门槛

未冻结完整范围时只能展示`P条已验收 / N条已登记`与“范围未冻结”，不得称完成百分比。冻结后，对模块m：

- N_m = 该冻结版本所有REQUIRED原子条目数（含未做/失败/阻断/缺证/陈旧证据）。
- P_m = N_m中独立review_status=PASS、证据VERIFIED、候选和清单绑定有效、所有依赖满足且未被撤销的条目数。
- 完成率_m = 100 × P_m / N_m。N_m=0或适用性UNRESOLVED时输出UNDEFINED，不输出100。
- 不适用项单独列出数量/依据，不进入分子或分母；范围调整必须披露与前一冻结版本的差异。
- 所有必需条目同权，条目粒度需审查防人为拆分；金额风险/安全优先级另列，不能以低风险大量通过抵消资金或越权失败。

“该版本约定内部范围100%”仅当范围完整性审查通过、N>0、P=N、无未解决需求/适用性、无失效证据、无未关闭阻断/强制依赖、当前候选集成门禁通过，且独立报告签发。不能写绝对“全系统永久100%”。100%内部验收不等于部署授权/运行SLA/团队在线/真实供应商接入。

整体展示延续既定口径：C01–C12模块完成率等权均值（仅在12个模块均已冻结且定义有效时），C13/C14单列；同时展示原子总数P/N作审计辅助，不混淆两种算法。称“C01–C14全部完成”须14模块各自满足100门槛。任何强制阻断未关，发布门禁HOLD，即使显示均值较高。

既有30/30/20/10/10五维0–4加权是“证据成熟度评分”，不是本条目完成率。前序70.2/100不能转成70.2%完成，也不作为新清单默认分子。两个指标必须命名分栏。

## 6. 本批重点用户旅程

C04/C11：真实客户查看当前押金/争议→回应/申诉→不同有权限审核者处理→刷新读取最新version/state→资金请求使用当前权威事实→同根余额/捕获/释放及原租金分离→用户/管理员看到真实结果。分别覆盖无损释放、取消释放、开案冲突、陈旧判决、重复并发、崩溃回滚、已产生资金后异议处理。页面存在不能当权限或账本证据。

C05：有权限运营者读取当前规则→按既有权限提交/审核/生效/撤销版本→未来订单选择当前规则，既有订单保留已接受版本→客户搜索/下单/取消显示同一政策与真实金额→unknown/retry和NO_REFUND_DUE正确→所有相关角色可达操作和审计。不得用客户手填hash/fixture文件路径替代正常运营UI，也不得把未经核验的审批引用当可信规则。

持续运营每模块至少有可复现“发现异常→任务登记→派发→受权执行/人工接管→验证结果→审计留存→后续复查”内部闭环，配置/登记/派发/执行/验证状态分开。真实长期在线观察按单独窗口报告；一次演练不能推出持续在线。

## 7. C13自身边界

C13审查者不开发自己正在验收的实现，发现项交开发团队；可写独立probes和报告。C13自身流程实现由其他受权开发者交付并由不同reviewer验证，不能用本文件定义直接自评PASS。本轮JSON原子清单全部NOT_ASSESSED，既有报告只作历史参考。香港前检标准和必要异常复核不重新开展全部质量验收，也不授予任何部署权；真人明确版本/环境/范围部署指令仍独立。
