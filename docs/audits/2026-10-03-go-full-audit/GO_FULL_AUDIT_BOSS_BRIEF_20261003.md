## 一、GO 今天真正做成的 5 件事

**1. 一个真的很好看的消费者 App（C 端）**
我打开 `staging-api.goaidirect.com/go-app/`，看到的是一个**真的商业旅行产品的样子**：顶上"GO SI DIRECT / 发现全世界，直接向官方预订"，五个品类（酒店、机票、火车票、租车、景点玩乐），两张入口卡片（"说出你的旅行想法"、"告诉酒店你的需求"），三句话讲清价值（直联、推荐、礼遇），下面三张旅行灵感图（京都、马尔代夫、里斯本），手机端还有底部导航（首页/行程/收藏/消息/我的）。
**这是真资产。**（截图已附）

**2. 全国酒店库 + 酒店页面生产**
这不是"页面模板"，是有一套真东西在跑：每家 **canonical hotel 有唯一系统身份（`hotel_id`）；酒店名称本身并不要求唯一**——但正因如此，改名/换牌需要别名与历史机制来承接，而**该机制目前还不存在（MISSING）**。此外有资料来源记录、有联系方式去重、有页面版本、有发布状态。工程上是完整的。

**3. 图片授权与发布审核台**
审核员真的能干活：能看到酒店身份对照、房型对应、原图授权、资料冲突，然后决定批准/发布/撤销。而且它有一个很专业的保护——**如果资料在审核过程中被改过，它会拒绝按旧资料批准**。
**全项目最像产品的一块。**

**4. 注册验证码 + 协议同意记录**
验证码有一次性的、有多重发送频率限制、有防重复提交。协议同意是**逐条记录的**（哪一条同意、哪一条延后、用的是哪一版、原文哈希）。这块质量高于多数商业系统。

**5. 登录/会话/权限**
登录、会话撤销、双因素、企业 SSO、防跨站请求伪造——这套基础是完整的。

## 二、看起来做成了、但其实没做成的 5 件事

**1. 消费者"能订酒店"**
打开酒店详情页，返回的是：**`hotel_test` / `GO Hotel` / `东京，日本`** —— 这是测试用的假数据（`hotel_test` 就是开发内部测试里用的那个假编号）。
首页的搜索条件也是写死的（`city_code: TYO`，日期 `2026-09-0x`）。
而且后台开关显示：**真实库存 = 关，真实价格 = 关，真实支付 = 关**。
**C 端界面做得很好，但它背后没有真实酒店库存，也没有真实收款。**

**2. 酒店供应商"能自己入驻"**
今天注册页**整个是灰的**，一个能点的都没有。（详见另两份专项报告）
就算修好，也会在"上传营业执照"那一步卡死——**我们让他填"营业执照资料引用"，但全系统没有上传文件的地方**。

**3. "供应商审核"**
我们有两个审批接口，但：
- 没有待审列表（审核员不知道有谁在等）
- 没有审核界面（审核员没有地方上班）
- 就算知道编号也审不过（见第三节第 1 条）

**4. "变更管理"**
代码里已经正确列出了四类高风险变更：**法律主体、地址、品牌、资质**——列表完全正确，而且提交后真的会产生一条记录。
但**全代码库没有任何一段代码能把它批准或驳回**。
也就是说：酒店要换牌、改名、换经营主体，提交完就永远躺在那儿。

**5. "供应商可以上传资料/签合同"**
合同在系统里**不是文件、不是一个对象，就是两个文本框**。谁生成、怎么签、属于谁、到期怎么办——一个都没定义。

## 三、最严重的 5 个现实问题

### 问题 1｜供应商入驻是一个"死圈"，转不出去

我们的规则是：**必须先有一家已经核验过的酒店，才能批准一个供应商。**
但我们又规定：**供应商在被批准之前，看不到也碰不了任何酒店相关的功能**（系统会直接拦掉）。
于是：要批准 → 需要酒店已注册；要酒店注册 → 需要知道酒店编号；要看编号 → 需要进后台；要进后台 → 需要被批准。
**每个出口都通向自己。**

**证据**：我们自己写测试的时候，是**直接往数据库里插数据**才跑通的。而且那个测试的名字就叫「需要先有酒店真相」——写测试的人心里清楚。

### 问题 2｜有一批内部接口，外面的人不用登录就能调用

我逐个检查了全部 1082 个接口，发现 **66 个没有做鉴权声明**。但我没有直接把 66 当成 66 个漏洞 —— 我逐条看了它们到底干什么，结果分成五类：

- **19 个是本来就应该公开的**（登录、注册、公开协议、健康检查、公开酒店图片、透明日志）；
- **2 个其实已经鉴权了**，只是写法不一样（在函数里判断，不是用标准写法）；
- **5 个是系统之间的回调**，已经用签名校验，**不该用「用户登录」那一套**；
- **35 个是真的应该鉴权但现在谁都能调** —— 这 35 个里 **25 个是内部管理接口**；
- 5 个需要产品判断是否有意公开。

所以我写进报告的准确数字是：**35 条该锁没锁，其中 25 条是内部的**，不是"66 个漏洞"。其中我在现场**不用登录就真的读到了真实业务数据**（包含真实的酒店编号）。另外还有几条我这次新发现的：**不用登录就能创建酒店预占**、**不用登录就能改任何一条评价的评分和内容**、**评价列表可以传别人的账号编号去读**。

其中我在现场**实际读到了真实业务数据**（未登录）：
- 酒店与连接器的映射漂移数据（里面能看到真实的酒店编号 `HRBUB`）
- 连接器健康清单
- 内部设计/代码冻结状态

另外这些**写操作**接口也是没鉴权的（我没有实际调用）：写供应商连接器凭据、审批酒店映射、认证连接器、触发表格重建作业、变更订单、变更 SLA。

**原因**：有个文件里明明 `import` 了鉴权工具，但**一行都没用上**。而且我们的安全中间件**只检查了跨站请求伪造，没有检查登录**。

顺便：`/docs`（接口文档）和 `/openapi.json`（全部接口定义，852KB）在公网上直接能打开。

### 问题 3｜运营人员"上班没有地方坐"

我数了运营后台的一级导航：**62 项**。
其中**第 11 到第 40 项连续 30 项**是"恢复控制、恢复实验、恢复学习、运行遥测治理、身份重签发、联邦信任执行、信用平面容灾、异常债务清理、预测漂移……"这类。

而**「供应商入驻审核」一项都没有**。

我算了一下：**恢复/信任/风险/预测这一类大概占全部接口的四分之一**。

（说明一下算法，避免被一个数字带偏：这四类的关键词计数相加是 691，**但那是重复计算的**——「预测」这一类 97 个接口**全部**已经包含在"恢复"的路径里。去掉重复后是 **305 个，占 28.2%**；按代码文件名归属算是 **287 个，占 26.5%**。我之前写的"64%"是口径错误，已经改正。）

### 问题 4｜"完成"没有定义，所以很多东西看起来完成了

这是最根子上的问题。我找到七种"看起来完成"：

| 看到什么 | 就以为 | 实际情况 |
|---|---|---|
| 表建了 | 功能完成了 | 变更申请表建了，但没人能批准（上面问题 4） |
| 接口有了 | 功能完成了 | 供应商审批接口有了，但审核员没界面、审不过 |
| 状态定义了 | 流程完成了 | 状态机有 10 个状态，但前端有一条走到死路 |
| 测试绿了 | 产品完成了 | 测试自己在往数据库插数据 |
| 有 Evidence | 业务验收完成了 | 验收用的是合成的假供应商编号 |
| CI 绿了 | 用户能用了 | 34 个 CI 里约 28 个验证的是"交付"，不是"产品" |
| PR 合并/部署了 | 产品正确了 | 指针写的是 PR320，现场跑的是 PR376，状态文档写的是 DEPTH48 的 PR52 |

### 问题 5｜指针和文档跟现实对不上（三处）

- 仓库里的「当前运行版本」写的是 **PR320**；现场实际跑的是 **PR376**（今天的）。
- 仓库里标注"这就是现场用的部署定义"的那份文件，**现场根本没用**——现场用的是 9 月 6 日的一份文件和部署工具生成的临时文件。
- 仓库里的「项目当前状态」文档绑定的是 **9 月 14 日**的版本，**落后 19 天**。

**后果**：任何人（包括 AI）以仓库文档为准去判断现状，都会判断错。

**另外一件事要如实说明**：用环境变量存运行时的密钥**本身是常规做法，不算设计错误**。真正的问题是：**这个 Key 的值在本次审计过程中被我的一次查询命令打印到了本地输出里**——也就是说它超出了"只留在服务器里"的范围。所以建议的动作只有一个：**把这张 Key 轮换掉**，并且以后审计不要再打印密钥内容。（值我不会写进任何文件。）

**关于接口文档公开**：`/docs` 和 `/openapi.json` 能公开打开，**这本身不算漏洞**。它的风险是"放大"——因为上面确实存在该锁没锁的接口，文档就把攻击面标好了。所以我的表述是「放大因子」，不是「漏洞」。如果产品以后有意对外提供 API 文档，那不该被当成错。

## 四、哪些已有资产不能推倒

这五样**方向对、实现对、现场在用**，要保住：

1. **酒店库与酒店页面生产**——有正式酒店身份、资料来源、联系方式去重、页面版本、发布状态。
2. **图片授权与审核台**——完整、专业、还带"资料被改过就拒绝旧资料批准"的保护。**可以拿它当其它审核台的样板。**
3. **上传管道的工程做法**——格式校验、查重、原子写盘、并发控制。做法是对的（只是用错了地方，用在了宣传图片上，没用在证件上）。
4. **注册验证码 + 逐条协议同意记录**——质量高。
5. **C 端界面**——真的像一个产品。

---

## 五、哪些工作应该立即停止

1. **停止继续扩张"恢复 / 信任 / 混沌 / 豁免 / 预测 / 遥测"这一类**（30 项导航、约 287–305 个接口）。它们服务的是一个还没有真实流量的系统。
2. **停止在还没想清楚的产品规则上建数据库表**（比如"酒店认领"、"合同"、"文件"、"员工关系"——这些的形状会替还没做的产品决定拍板）。
3. **停止把"表/接口/状态/测试/证据存在"当作功能完成**。
4. **停止在生产面上留着没鉴权的内部接口**。
5. **停止公开 `/docs` 和 `/openapi.json`**。

## 六、哪些工作应该立即开始

1. **处理 35 条该锁没锁的接口**（优先其中 25 条内部接口，特别是「写连接器凭据」和「审批酒店映射」两条）+ **轮换**被暴露的 Key + 决定接口文档是否对外（按「放大因子」处理，不是漏洞）。
2. **把供应商入驻那个死圈解开**——要定的**不是二选一**，而是一件事：**「主体认证（这家公司是谁）」和「酒店关系认证（这家公司有权经营哪家酒店）」这两件事，分别在入驻的哪一步发生、谁先谁后、最后什么条件才解锁经营后台。** 目前系统把两件事互相设成对方的前置条件，所以谁也走不到头。**只要把这两个阶段的先后关系定义清楚，死圈就解开了。**
3. **给运营一个入驻审核台**（照抄酒店图片审核台的做法）。
4. **做真正的文件上传**（营业执照、身份证明、门头照、合同）——**这是目前最明确缺失的核心底层能力之一**（不是唯一缺的：审核台、找回密码、通知、正式合同对象也都要新增）。
5. **补上：找回密码、入驻结果通知、合同对象**。
6. **接上真实供给和真实支付**——否则 C 端界面再好也只是展示品。
7. **最后**才轮到治理。

## 七、为什么 PR / CI / Evidence 以前会让人误以为产品已经完成

**因为我们实际上用的"完成"标准是"存在性"，不是"能不能用"。**

- 表存在 → 当成功能完成
- 接口存在 → 当成功能完成
- 状态存在 → 当成流程完成
- 测试通过 → 当成产品完成（**但测试自己在插数据库**）
- Evidence 存在 → 当成验收完成（**但验收用的是合成供应商**）
- CI 绿 → 当成用户可用（**34 个 CI 里约 28 个验证的是交付链，不是产品**）
- 部署成功 → 当成产品正确

**这不是执行不力。这是缺少一个"完成"的定义。** 新的定义我写在 `GO_FULL_AUDIT_BOSS_GPT_HANDOFF_20261003.md` 里（一个功能必须同时有：产品规则、数据模型、成功路径、失败路径、用户界面、运营界面、恢复方式、通知、真实流程测试、运行时验收——**才能叫 PRODUCT_DONE**；否则只能叫 DESIGN_ONLY / BACKEND_ONLY / UI_ONLY / TECHNICAL_PROTOTYPE / DELIVERY_ONLY）。

## 八、如果明天就给真实用户使用，会发生什么

| 谁 | 会发生什么 |
|---|---|
| **一个消费者** | 打不开网站首页（根地址是 404，必须知道 `/go-app/`）。就算进去，搜到的是测试数据。**订不了房。** |
| **一家酒店** | 打开注册页，**所有按钮都是灰的**。就算修好，会在"上传营业执照"卡死。忘密码也没法找回。 |
| **一个运营人员** | 交易、退款、内容审核能做。**但供应商入驻审核没地方做**——他不知道有谁在等，也没有界面。 |
| **一个安全人员** | 会发现 **35 个该锁没锁的接口不用登录就能调（其中 25 个是内部接口，包括写凭据和审批映射）**；不用登录能创建酒店预占、能改任意评价；接口文档和全量 API 定义对外可读（放大因子）；一张第三方 Key 建议轮换。 |

**结论：不能上线。** 不是"差一点"，是**四类人都走不通**。

---

## 九、下一阶段正确目标

**不要追求"再补几个功能"。目标应该是三句话：**

1. **让一个真实酒店能在没有人指导的情况下走完入驻**（并且运营人员不用碰数据库就能审完）。
2. **让一个真实消费者能真的订到一间真的房**（真实库存 + 真实收款）。
3. **在该有审核的地方，都有一个运营人员能用的工作台**。

以及一条纪律：

> **以后任何功能，都从"一个真人能不能走完"开始定义，而不是从"表建好了没有"开始。**

---

## 十、一句话总结

> **我们花了很多工程把"别出错"做到了极致——字节级校验、双签、哈希、审计、保留期、预测、混沌、信任平面。**
> **但"这件事本身"还没做完：一个酒店要交什么、交给谁、谁来看、看完怎么办。**
> **现在最该做的不是继续加治理，而是把"用户要走的那条路"当成唯一目标，把它走通。**

## 附：我是怎么得出这些结论的

- **只读**：全程没有改动任何代码、数据、配置或部署。
- **实测**：用浏览器在多个屏幕尺寸下真的打开了三个系统（消费者端、供应商端、运营端），截图已附。
- **逐个检查**：把全部 **1082 个接口**、**563 张数据表**、**供应商端 72 个路由入口（10 个主入口 + 62 个隐藏入口）**、**62 个运营界面**、**34 条 CI 流水线**都过了一遍，并写进 `GO_FULL_AUDIT_INVENTORY_20261003.md`（覆盖清单）。
- **该收的口径都收了**：本版相较初版更正了三处容易被反驳的统计（治理占比 64%→26.5%、`/internal/*` 不等于 admin-only、66 条无鉴权→分类后 35 条），**并撤回了 1 条我判断错的 finding**。逐条 OLD→NEW→WHY 见 `GO_FULL_AUDIT_ERRATA_20261003.md`。
- **一处反向证据**：563 张表里 **560 张确实被代码引用**，只有 2 张是孤儿。所以问题**不是**"建了一堆没人用的空表"，而是**"表都进了程序，但它们服务的那条业务路真人走不通"**。
- **对不上就写对不上**：凡是拿不到证据的，报告里一律写 `UNKNOWN`，不猜。
