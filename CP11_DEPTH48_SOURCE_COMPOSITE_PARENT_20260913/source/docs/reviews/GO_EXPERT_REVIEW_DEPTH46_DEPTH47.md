## 已确认发现

### GO-ER-01 · P1：GO Direct 已放弃差额会重新变为可用价值

用户规则是改期零手续费、原订单固定 365 天、每次升价补差、降价差额放弃。普通酒店已按当前房价计算下一次补差，并独立累计已放弃价值；Direct 仍使用保留的最高订单金额作为基数。

| 隔离复现路径 | 应有结果 | 实际结果 |
| --- | --- | --- |
| ¥1,620 → ¥1,400 → ¥1,500 | 第二次改期补 ¥100；此前 ¥220 继续放弃 | 补 ¥0，订单金额仍为 ¥1,620 |
| ¥1,620 → ¥1,400 → 转住宿额度 | 可用额度 ¥1,400，¥220 不恢复 | 实际发出且可用 ¥1,620 额度 |
| 普通酒店降 ¥432 → 再升 ¥100 | 补 ¥100 | 补 ¥100，对照通过 |

根因位于 [`hosted_fare_change.py`](https://github.com/yuguangzhi3836-glitch/GO/blob/1df7c3592f6818114363c078c2509445923f974d/application/src/go_hotel/services/hosted_fare_change.py)：`difference=max(0,quoted-r.amount_minor)`，并将 `r.amount_minor` 保留为旧金额加正差额。实际每晚房价已经降低，但下一次报价仍读取保留金额。随后 [`hosted_stay_credit.py`](https://github.com/yuguangzhi3836-glitch/GO/blob/1df7c3592f6818114363c078c2509445923f974d/application/src/go_hotel/services/hosted_stay_credit.py) 直接以 `r.amount_minor` 发行额度，导致放弃差额恢复。

该保留金额算法在 DEPTH46 对应源码中也存在，不能将其描述为 DEPTH47 新引入的回归。现有 Direct 测试覆盖单次降价和连续升价，且接受保留金额行为；没有覆盖这两条跨操作组合。此次只证明模拟环境中的规则违背，不声称发生了真实资金损失。

修复验收：分别记录当前住宿价值、累计放弃价值与资金来源；报价、改期、续住、转换额度、退款和 GO Trip 使用一致的价值模型。保留原授权/扣款不可变事实，不能简单覆盖总额或新增一套支付系统。必须覆盖降→升、升→降→升、降→转换、降→续住→转换、失败回滚和重复提交，并同时核对资金、额度、库存和订单终态。

### GO-ER-02 · P1：往返与多程机票改签尚未实现

[`flight/service.py`](https://github.com/yuguangzhi3836-glitch/GO/blob/1df7c3592f6818114363c078c2509445923f974d/application/src/go_hotel/flight/service.py) 的 `change_quote` 对任何非单航段订单直接抛出 `MULTI_LEG_CHANGE_NOT_IMPLEMENTED`。

本轮使用两程均允许改签的 GO Flex 票价，原去程第 10 天、回程第 14 天，请求改为第 12 天，实际 HTTP 422。既有 [`test_flight_journey_depth.py`](https://github.com/yuguangzhi3836-glitch/GO/blob/1df7c3592f6818114363c078c2509445923f974d/application/tests/test_flight_journey_depth.py) 正是断言该拒绝行为，应保留其防止误改单程的保护价值，但不能把它当成多程改签验收。

修复验收：明确改签航段及适用乘机人，完整保留未变航段、票号归属与已接受条款；按所选票价报价、确认补款、等待供应商结果，失败恢复原有效行程，响应丢失不重复出票/扣款。往返只改去程、只改回程，多程只改中间程，分别核对消费者、供应商、管理员和 GO Trip 的同一订单。儿童/婴儿、同日往返等扩展能力另列产品范围，本轮不擅自将其计为已批准必做项。

### GO-ER-03 · P2：主线 README 仍指向过时父包

本轮实时读取的 [main 固定提交 README](https://github.com/yuguangzhi3836-glitch/GO/blob/1c9847c82725b888d239686572f1f44b6dafc2cc/README.md) 仍写 DEPTH41、1300 个应用文件、PR47 Draft、`MERGE=NO` 以及 main 尚未合并。实际 PR47 已合并且父包已到 DEPTH46。

这会使新窗口或接手人员从旧版本重新工作。PR52 已包含入口文档修正，但尚未进入 main。关闭条件：主线入口、候选身份及父包身份一致，同时清楚记录 PR52 未合并/未入包的状态。该发现涉及描述性版本信息，不改变现有授权规则。

### GO-ER-04 · 验收缺口：当前源码还没有完整三端与 PostgreSQL 证据

这是未验证范围，不是已经复现的代码错误。当前 PR52 的 PostgreSQL 6 项竞争检查、完整新浏览器路径及真机体验尚未执行。历史 PASS 不能替换这些检查。

## 本次评审决议与修复顺序

1. **首先修复 ER-01。** 建立 Direct 与普通酒店一致的价值模型，先让本轮两个金额断言通过，再扩展相关取消、续住、额度及资金/库存组合检查。当前父包作为已知基线保留，记录其已知缺陷。

3. **同步统一版本入口与模块验收表。** 继续沿 PR52 应用候选深化；本评审文件的归档分支不产生第二条应用开发基线。不因 CI 额度耗尽恢复旧 PR48 并行开发。
4. **六品类以同单完成业务、资金、库存/票据和三端四层核对。** 每项标明：已实现、当前源码已验证、缺失、待验证。规则保持用户要求的简单清楚，内部恢复措施不能增加无意义的用户审批步骤。
5. **最后进行三端体验与新父包验收。** 消费者完成任务，供应商处理结果，管理员核对异常；逐屏验证信息层级、状态反馈、表单、导航、移动适配与无障碍后才评分。候选稳定后补齐可用的 PostgreSQL/浏览器检查并生成新的父包，保留原包哈希与新包身份。

“全部闭环”的验收单位应是具体业务场景：搜索→报价→同意→预订→支付→供应商确认→履约→适用退改/退款→GO Trip 最终状态；再叠加报价过期、权限变化、并发、库存不足、供应商拒绝、响应丢失及进程中断等适用分支。明确不适用的步骤应记录业务理由，不能靠删除测试或把拒绝结果标作功能完成来获得全绿。
