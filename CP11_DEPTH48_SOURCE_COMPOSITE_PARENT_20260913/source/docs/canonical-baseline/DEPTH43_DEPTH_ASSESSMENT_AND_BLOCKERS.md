## 当前难点与处理方向

### 1. 新增复杂流程仍缺可重复的完整浏览器验收

现有 CI 浏览器旅程已成功运行，说明并非所有浏览器渠道都不可用。当前会话先前的 4187 访问留有被阻断的错误摘录，但原消息导出、绝对执行时间和唯一会话／环境标识仍未取得。本轮未重新访问该入口。

建议优先检查并扩展已经工作的、获准的隔离 CI 浏览器流程，加入订单搜索、酒店改期、补款失败恢复及退款恢复的实际界面操作；执行时绑定新的固定源码和运行标识。此方向尚未实施，不保证无需进一步环境适配。

4187 历史原件的缺失应保留为独立证据缺口；不应据此推断所有隔离环境都不可用。新的运行结果必须独立归档，不能倒填旧尝试的时间或替代其原件。

### 2. 复杂业务组合的覆盖仍不足

真正耗时的部分是证明同一订单在多端、多次变更和失败恢复后仍保持日期、供应商归属、状态及资金一致。仅有支付成功或退款请求成功不足以完成此项。

建议把每类业务整理为有限、可检查的矩阵：正常完成、用户取消、供应商拒绝、结果不明、付款失败、退款失败、重试与重复请求；再补该品类特有的改期、补款、押金等路径。共享底座可复用，品类差异必须明确保留，不能仅以酒店通过代替其他品类。

### 3. PostgreSQL 与原生设备存在实际验收缺口

六项 PostgreSQL 检查目前跳过，SQLite 通过不能证明数据库并发与事务行为相同。方向是在隔离 PostgreSQL 环境验证当前源码；不需要因此访问 RDS。

iOS／Android 当前有源码、类型与契约检查，尚无完整设备旅程。移动网页可覆盖一部分体验，但不能替代原生设备证据。

### 4. 业务功能与外部接入需要分别报告

沿用用户已明确的范围：真实库存、真实报价和真实银行接入不要求在上线前同步完成，相关功能可使用明确标识的测试数据与隔离适配器验收。必须分别报告功能实现、隔离闭环和外部接入状态。

真实供应商或银行尚未接入，不应阻止可独立完成的源码和隔离测试；也不能因为隔离通过而声称外部接入已经完成。

### 5. 流程有简化空间，但现有治理不是全部阻塞的原因

已阅读 PR41 与 CHANGE_CONTROL_POLICY.md。它们要求唯一来源、GitHub 审查轨迹、明确变更类别及运行操作边界，没有要求每个普通修复都向用户重新申请一次批准，也没有要求任何一项 HOLD 都停止其他已授权工作。

当前 PR47 有明确的统一候选修复路径。历史供应商认证输入修订曾被审批限制的具体原始拒绝理由，本轮未取得；不能笼统宣称整项开发必须停工，更不能改写规则绕过该限制。
