## Database and recovery contract

`expected_head` is the immutable image's Alembic source head; `database_head` is the separately approved live database revision for that image. Both are checked exactly. They are not silently made equal or inferred from history.

For R3.1.5, a profile declaring database 0132 while its source head remains 0114 is **not an assertion of compatibility**: such a site binding requires independent old-application-on-0132 compatibility and restore evidence. Current HK evidence does not establish this. DEPTH40 requires both heads at 0132. Service-only deployment/rollback refuses a transition between different database revisions; migration and database restoration are never performed by this executor.

The recovery preparation is a separate signed document with purpose `DEPLOY_FAILURE_RECOVERY_PREPARATION`, authority `GO-COMMAND-CENTER`, environment `HK-STAGING-01`, status `APPROVED`, exact previous/candidate profiles, expiration, and SHA-bound backup/restore evidence and stop/restore procedure. `automatic_recovery` must be false and `fresh_recovery_authorization_required` true. The existing task verification public key verifies it; this repository does not create a real approval/signature or modify a key. An approved preparation is not a recovery Task.

The current successful-DEPLOY-only rollback schema remains enforced. A failed source is never relabeled SUCCESS to make it eligible. Partial deployment failure requires Command Center's independently authorized recovery handling and the preserved durable state. The new check prevents that missing preparation from being overlooked; it does not claim a real recovery has been proven.

## Site binding and installation boundary

The entrypoint deliberately ships with `SITE_BINDING_SHA256 = None` and no active `site-binding.json`. Any real action fails closed before a Docker call. A final site package must separately seal the exact reviewed binding and entrypoint bytes; the binding file and parents must be root-owned and not group/world-writable or symlinks. Tasks cannot supply paths, resource names, Docker flags or environment variables.

The binding contains exactly `schema_version`, `environment`, `project`, `candidate`, `previous`, `network`, `media_volume`, and `recovery_plan`; profile fields are `image_id`, `repo_digest`, `compose_path`, `compose_sha256`, `env_path`, `env_sha256`, `layout`, `expected_head`, `database_head`. The code is the executable schema. Use actual approved values; do not convert UNKNOWN into placeholders that pass a check.

No installer, task publisher, key provisioner or TEST_PR handler is provided. Current Agent compatibility with the new installed executor fingerprints/output and the recovery-preparation workflow still needs controlled installation acceptance. Historical task IDs/nonces are never reused.

The suite uses real Python, temporary filesystem records and ephemeral test Ed25519 keys. Docker is a command-level model. Its 34 tests do not prove actual Docker Compose, Hong Kong transport, three-end browser login, queue/E2E behavior or a successful rollout.

The read-only-permission PR workflow downloads **only GO artifact 10186084217**, checks the fixed outer ZIP SHA `715b939feb5529fcd97860ed921e5b292a874a2cbfacae0706a4da39023aad4f`, checks the original delivery files/parts/config, builds the child without network access, reloads the exported child archive, checks unchanged source bytes, and tests the repaired type guard against a dedicated PostgreSQL 18.4 fixture. Read the run outcome and `GATE_REPORT.json` before asserting success.
